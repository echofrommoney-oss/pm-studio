# 自動測試工作流

> 目的不是測試數量，而是讓驗收清單上能自動驗的項目都有測試、每次改動都能一鍵確認沒壞。
> 使用者在工作台右欄「QA」按「全部執行」看結果；每個驗收項旁邊顯示有沒有自動測試、有沒有通過。

## 觸發方式

- 使用者說「自動測試」「寫測試」「QA」「測試覆蓋」
- 工作台按「QA → 自動測試」

## 前置

1. `ARCHITECTURE.md` 的 services 要寫明怎麼跑測試：
   - Flutter、Supabase 已內建（`flutter test --machine`、`supabase test db`）。
   - 其他服務要有 `test`（測試指令）與 `test_report`（JUnit XML 報告位置）。沒有 → **不要自己改 `ARCHITECTURE.md`**，在回覆中列出建議的設定，請使用者按「系統設計」補上，然後結束本輪。
2. 本需求要有驗收清單（`[需求名]/驗收清單/`，每個驗收項有 `data-id`）。沒有 → 先走 `pm-acceptance.md`。
3. 讀技術規格（`manifest`、邊界與錯誤處理、權限）與 `ARCHITECTURE.md` 的角色權限表。

## 測試工具

用 `ARCHITECTURE.md` 選定的技術生態裡**最普遍**的工具，並設定輸出 JUnit XML，例如：

| 技術 | 常見工具 | JUnit 輸出 |
|---|---|---|
| Flutter | `flutter_test`、`integration_test`（需要系統權限彈窗時用 Patrol） | 工作台直接讀 `--machine` 輸出，不用另外設定 |
| Supabase | pgTAP（`supabase/tests/*.sql`） | 工作台直接讀 TAP 輸出 |
| Node／TypeScript | Vitest、Jest、Playwright（網頁流程） | `--reporter=junit`、jest-junit、Playwright 的 junit reporter |
| Python | pytest | `--junitxml=路徑` |
| 其他 | 該生態的主流工具 | 多數有 JUnit 輸出選項或轉換工具 |

沒有把握的選擇（例如要不要引入 Playwright）先問使用者，不擅自加大型依賴。

## 寫什麼

依驗收清單逐項判斷「能不能自動驗」：

- **能**：資料規則、權限（A 角色看不到 B 的資料）、API 回應與錯誤碼、表單驗證、狀態流轉、畫面流程的主要路徑。
- **不適合**：視覺美感、文案語氣、實機推播到達、需要真人判斷的體驗。這些留給人工驗收，在回覆中列出。

每個能自動驗的項目寫至少一個測試，分三層：

1. **後端**：資料表權限規則、API／函式的正常與錯誤情境。用「後端 → 帳號」的測試帳號或在測試裡自建測試資料，**不依賴示範資料的內容**。
2. **APP／前端**：元件與畫面的主要互動；網站的主要流程可用瀏覽器自動化，失敗時截圖。
3. **跨端流程**（選做）：例如「飼主在 APP 設定提醒 → 管理後台看得到」，只挑最關鍵的一兩條。

## 標記：對應到驗收項

測試名稱裡加上：

```
[驗收 需求名:驗收項編號]
```

例如 `test('[驗收 疫苗提醒:提醒-新增-1] 飼主可以新增疫苗提醒', ...)`。一個測試可以帶多個標記；編號必須和驗收清單的 `data-id` 一字不差。工作台據此顯示覆蓋狀況，標錯的編號會被列出來。

## 執行與完成

1. 用服務的測試指令跑一次（指令已在允許清單內）。**需要服務在執行的測試**（例如打 API、瀏覽器流程），請使用者先在右欄啟動對應服務；不要自己啟動開發伺服器。
2. 失敗的測試：
   - 是測試寫錯 → 修測試。
   - 是程式真的有 bug → **不要順手改程式**，在回覆中列出，請使用者按「除錯」處理（修 bug 是另一件事，分開提交才看得清楚）。
3. `python3 scripts/pm_sync.py commit 需求名 -m "[需求名] 自動測試：新增 N 個測試，涵蓋 M／K 個驗收項"`。
4. 回覆使用者：涵蓋了哪些驗收項、哪些只能人工驗、有沒有發現 bug、請他在右欄「QA」按「全部執行」確認。
