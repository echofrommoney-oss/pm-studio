# 系統設計工作流（SA/SD）

> 每個需求的技術規格（`pm-spec.md`）只看自己那一塊。`ARCHITECTURE.md` 是整個產品的總藍圖：用什麼技術、系統怎麼分、資料彼此怎麼關聯、誰能碰什麼。
> 它放在專案根目錄，和 `PRODUCT.md`、`DESIGN.md` 並列，一個專案一份，永遠是最新版。

## 觸發方式

- 使用者說「系統設計」「架構」「SA」「SD」「技術選型」「資料庫設計」
- 工作台按「系統設計」
- 第一次寫技術規格或第一次開發前，專案沒有 `ARCHITECTURE.md`

## 前置

1. 讀 `PRODUCT.md`（平台、使用者、限制）、`DESIGN.md`。
2. 讀所有需求資料夾的 PRD，掌握產品全貌；已有技術規格的也讀。
3. 看專案裡有沒有程式碼（`app/`、`web/`、`supabase/`）。有 → 以現況為準，描述現況並標出要調整的地方。

## 預設技術組合

使用者沒有另外指定時，採用工作台支援的組合。**使用者指定別的，就照使用者的，並在回覆中說明哪些工作台功能會受影響**（例如不用 Supabase，後端分頁的資料庫與帳號管理就無法使用）。

| 部分 | 技術 | 程式位置 |
|---|---|---|
| APP | Flutter（Dart） | `app/` |
| 前端 | Next.js（TypeScript），管理後台、合作夥伴網頁、官網三個網站 | `web/admin/`、`web/partner/`、`web/site/` |
| 後端 | Supabase（Postgres、Auth、Storage、Edge Functions、pg_cron） | `supabase/` |

產品不需要某一部分（例如沒有合作夥伴網頁），就不列。

## 產出：`ARCHITECTURE.md`

```markdown
# [產品名] 系統設計

> 最後更新 YYYY-MM-DD

## 1. 技術組合
表格：部分｜技術｜版本要求｜程式位置｜用途。附一句選型理由。

## 2. 系統架構
Mermaid `flowchart`：使用者端（App、各網站）→ Supabase（Auth、資料庫、Storage、Edge Functions、排程）→ 第三方服務（推播、地圖、金流、寄信…）。
每個第三方服務一行說明：做什麼、在哪一端呼叫、金鑰放哪。

## 3. 角色與權限
| 角色 | 說明 | 從哪登入 |
接著一張「角色 × 資料」權限表：每種資料每個角色能 讀／新增／修改／刪除 哪些（例如「飼主：只能讀寫自己的貓」）。
這張表是所有資料表 RLS 規則的來源。

## 4. 資料模型
Mermaid `erDiagram`：全產品的資料表與關聯。
每張表一行：用途、屬於哪個需求、主要欄位（完整欄位在各需求的技術規格）。
命名慣例：資料表與欄位用英文 snake_case 複數表名；每張表都有 id（uuid）、created_at、updated_at。

## 5. 後端慣例
- 資料表：一律開 RLS；權限依第 3 節。
- 什麼放資料庫函式（RPC）、什麼放 Edge Function、什麼放排程。
- 檔案儲存：bucket 清單、公開或私有、路徑規則。
- 錯誤格式與錯誤碼慣例。

## 6. 前端與 APP 慣例
- 狀態管理、路由、資料存取方式（APP 與網站各一段）。
- 設計 token：由 `DESIGN.md` 產生，不手寫色碼。
- 多語系、時區、日期格式。

## 7. 環境
| 環境 | 用途 | 資料 |
本機（工作台、示範資料）→ 測試環境 → 正式環境。金鑰與環境變數清單（只列名稱與用途，不寫值）。

## 8. 非功能需求
效能、安全、隱私、個資、備份、監控的全產品基準。沒有依據的數字寫「待確認」。

## 9. 待確認
```

## 寫法

- 名稱與 PRD、技術規格一致；資料表名第一次出現時附中文說明。
- 圖一律用 Mermaid。
- 不編造：流量、效能指標、預算沒有依據就寫「待確認」。
- 只留最新版，不寫修訂紀錄；修改理由寫在 git 提交訊息。

## 和其他文件的關係

- 技術規格（`pm-spec.md`）依本檔寫；本檔的資料模型是各需求 Spec 資料表的總表。
- 本檔改了 → `pm_sync.py` 會把所有需求的技術規格標為待同步，走 `pm-change.md` 一起改。
- 後端開發（`pm-backend.md`）的 RLS、命名、bucket 都依本檔。

## 完成後

1. 自查：每個 PRD 的主要資料都在資料模型裡有落點；每張表在權限表裡都有規則。
2. `python3 scripts/pm_sync.py commit 需求名 -m "[需求名] 系統設計：一句話摘要"`（本檔在專案根目錄，commit 指令會一併提交）。
3. 回覆使用者：技術組合、有幾張表、幾個角色、幾條待確認。
