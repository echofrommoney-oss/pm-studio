# 技術規格（Spec）工作流

> PRD 回答「要做什麼、長什麼樣」，而且刻意不寫技術細節（`pm-prd.md` §2.3.1 ⑤）。
> Spec 回答「工程上怎麼接」：資料、狀態、介面、權限、錯誤、非功能需求。它是 PRD 的技術翻譯，不重新定義產品行為。

## 觸發方式

- 使用者說「技術規格」「Spec」「給工程師」「技術交接」「開發文件」
- PRD 與原型已完成（最好也通過 `pm-prd.md` §3.7 設計關卡）

## 前置

1. 讀 `[需求名]/需求文件/[需求名]-PRD.html`（必要）與 `[需求名]/原型/`（必要），有流程圖一併讀。
2. 讀 `PRODUCT.md` 的平台與限制段。
3. **看專案裡有沒有程式碼。** 有（例如有 `package.json`、`src/`、`app/`、資料庫 schema、API 路由）→ 以現有技術棧與命名慣例為準，Spec 描述「要在現有系統改什麼」。沒有 → 問使用者一次技術棧；使用者不知道或還沒定，就寫成與技術棧無關的形式（資料實體、狀態、介面契約），實作細節標「待工程確認」。
4. **不編造。** 沒有依據的數字（效能指標、配額、保留天數）一律寫「待工程確認」或「待產品確認」，不要自己填一個合理的值。

## 產出

`[需求名]/技術規格/[需求名]-spec.md`（Markdown：工程師會放進 repo、在編輯器裡讀、在 PR 裡引用）。

只有一份，永遠是最新版。**不寫修訂紀錄。**

## 結構

依需求實際需要取捨章節，沒有內容的章節整章不寫（不留「無」）。

```markdown
# [需求名] · 技術規格

> 對應 PRD：[需求名]/需求文件/[需求名]-PRD.html · 最後更新 YYYY-MM-DD

## 1. 範圍
這次工程上要動什麼（新增／修改／移除），不做什麼（沿用 PRD「本期不做」）。一段話加一個清單。

## 2. 頁面與路由
| 原型頁面（hash） | 路由／畫面 | 進入條件 | 備註 |
每一列對應原型的一個 `#page-id`，工程師可以直接點原型對照。

## 3. 資料模型
每個實體一個小節：用途、欄位表（名稱｜型別｜必填｜預設｜限制｜說明）、與其他實體的關係。
新增欄位與既有欄位分開標示。

## 4. 狀態與流轉
有狀態的實體畫 Mermaid `stateDiagram-v2`：每個狀態的意義、觸發轉換的事件、不允許的轉換。
複雜編排畫 `sequenceDiagram`（本需求有 Spec 時，時序圖只放這裡，PRD 省略該章）。

## 5. 介面
每個介面：方法與路徑（或事件名／函式名）、用途、請求欄位、回應欄位、錯誤情況與錯誤碼、冪等性、權限。
沿用既有 API 風格；沒有既有系統時用 REST 慣例描述，標示「格式待工程確認」。

## 6. 權限
| 角色 | 能看 | 能做 | 不能做 |

## 7. 邊界與錯誤處理
從 PRD 詳細方案每一行的【邊界說明】整理成工程視角：觸發條件 → 系統行為 → 使用者看到什麼（引用 PRD 文案，不另寫）。

## 8. 埋點實作
對照 PRD「資料埋點」表：事件名、觸發時機（精確到哪個動作完成後）、參數來源欄位。PRD 沒有埋點章節就省略。

## 9. 非功能需求
效能、安全、隱私（個資欄位、保留與刪除）、可存取性、相容性（瀏覽器／OS 版本）、可觀測性（要記哪些日誌）。沒有依據的數值寫「待確認」。

## 10. 遷移與相容
既有資料怎麼處理、舊版客戶端怎麼辦、是否需要功能開關、上線順序。

## 11. 測試重點
工程自測要涵蓋的情境，對應到驗收清單的模組（不重複驗收清單全文）。

## 12. 待確認
工程或產品還沒決定的事，一條一句。確認後把結論寫進上面對應章節並從這裡刪掉。
```

## 寫法

- **與 PRD 同一套名稱。** 頁面名、功能名、狀態名、按鈕文字和 PRD、原型一字不差，工程師才對得起來。
- 表格優先於段落；每一列一件事。
- 用 Mermaid 畫圖（工程師的工具鏈大多直接渲染 Mermaid）。
- 不重抄 PRD 的產品描述，寫「見 PRD 詳細方案〈二級功能名〉」即可。
- 文案、錯誤訊息引用 PRD 原文，不自己改寫。

## 完成後

1. 自查：Spec 裡每個頁面都能在原型找到對應 hash；PRD 詳細方案的每一行在 Spec 都有落點（資料、介面或「無工程變更」）。
2. `python3 scripts/pm_sync.py status 需求名`：沒有落後項就 `mark`；有就在回覆中提醒使用者（見 `pm-change.md` 步驟六）。 最後 `python3 scripts/pm_sync.py commit 需求名 -m "[需求名] 技術規格：一句話摘要"`（見 `pm-change.md` 步驟六）。
3. 回覆使用者：Spec 放在哪、有幾條待確認。

## PRD 改了之後

走 `pm-change.md`。Spec 在它的下游清單裡，會被一起改到一致。
