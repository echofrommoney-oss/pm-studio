# 變更管理工作流

> 需求改了，所有受影響的文件就一起改，改完每份文件都是**最新且彼此一致**的版本。
> 不寫變更紀錄、不留舊內容、不加「已修改」標記。使用者看到的永遠是現在成立的東西。

## 觸發方式

- 使用者說「改一下」「調整」「客戶要加／拿掉 xxx」「這裡不對」「同步一下」
- 工作台顯示某份文件「落後於 PRD／DESIGN.md」
- 原型驗證的結論要落回文件（`pm-validate.md` 步驟四會呼叫這裡）
- `DESIGN.md` 改了，已有的原型與落地頁要跟上

## 文件之間的關係

改了左邊，右邊就要檢查：

| 改了 | 要一起檢查的 |
|---|---|
| PRD（`需求文件/`） | 原型、業務流程圖與互動流程圖、原型驗證腳本、技術規格、驗收清單、上線文件（版本說明、商店文案、落地頁文案） |
| 原型（`原型/`） | PRD 對應的詳細方案行（反向）、原型截圖（重新匯出）、互動流程圖、原型驗證腳本 |
| 流程圖（`流程圖/`） | PRD 流程描述（反向）、流程圖截圖（重新匯出） |
| 技術規格（`技術規格/`） | 若工程面的修改改變了產品行為 → PRD（反向）與驗收清單 |
| `DESIGN.md` | 本專案**所有需求**的原型、落地頁；原型截圖重新匯出 |
| `ARCHITECTURE.md` | 所有需求的技術規格；已開發的程式（`supabase/`、`app/`、`web/`） |
| 驗收清單 | 自動測試的驗收標記（編號改了或項目刪了，測試名稱跟著改）；QA 分頁會列出對不上的編號 |
| 技術規格（程式已開發時） | 對應的後端遷移、函式、示範資料，以及 APP 與網站程式。程式的修改走對應的開發工作流（`pm-backend.md` 等），且**只能新增遷移檔，不改已套用的** |
| `PRODUCT.md` | 通常只影響之後的新工作；定位或目標使用者改變時，列出可能受影響的 PRD 請使用者決定 |

`python3 scripts/pm_sync.py status 需求名` 會依這張表列出目前落後的文件，開始前先跑一次。

## 步驟

### 一、弄清楚改什麼

把使用者的話整理成一句「變更內容」，例如「課程收藏上限從 50 改成不限」。一次對話提了好幾件事就逐條列。

**需要先確認才動手的情況**（列出影響範圍，請使用者回覆「可以」後才改，以編號清單作為本輪最後的回覆）：

- 會刪掉整個頁面、整個功能或整份文件
- 影響不只一個需求（例如改 `DESIGN.md`、改共用規則）
- 和 PRD「本期不做」或 `.pm-workflow/context/[需求名].md` 裡的使用者約束衝突
- 會改變技術規格裡已經給工程師的資料結構或介面

其餘情況直接改，不必先問。

### 二、找出影響範圍

1. 跑 `pm_sync.py status 需求名`，看既有的落後項。
2. 依上面的關係表，逐份讀相關文件，找出**真正提到這件事**的位置（不是所有下游都一定要改）。
3. PRD 內部照 `pm-prd.md` §5.3 的位置清單逐項檢查。

### 三、由上游往下游改

> **改長文件的方式**：用精準的字串替換逐段修改，不要反覆整份讀取再整份寫回。幾百行以上的文件重讀一次就是一次完整的用量，大規模合併最容易在這裡燒掉額度。先用 grep 找到要改的位置，再針對那一段替換；改完一段直接下一段，不必重新確認全文。


順序固定，避免下游先改完又被上游推翻：

```
PRODUCT.md / DESIGN.md / ARCHITECTURE.md → PRD → 流程圖 → 原型 → 原型驗證腳本 → 技術規格 → 程式（後端 → APP → 前端）→ 驗收清單 → 上線文件
```

每份文件的改法：

- **直接改成新的樣子。** 舊內容刪掉，不劃線、不註記「原為」、不加「（已修改）」。
- 刪掉的頁面或功能：從 PRD 詳細方案、原型、流程圖、技術規格、驗收清單都拿掉；原型的 `pages` 陣列、PRD 雙欄預覽的 `CATALOG` 與 `data-preview` 一併清掉。
- 被取代的檔案直接刪除，不改名成 `-old`。唯一例外是使用者明確說要保留。
- PRD「專案資訊」的「最後更新」與副標題日期改成今天；功能範圍有實質變化時版本號遞增。其他文件若有日期欄位也同步。
- 待確認清單：已經有結論的條目，把結論寫進正文對應位置並從清單刪掉。
- 驗收清單重新產生時，保持驗收項的 `data-id` 穩定（用「一級模組-二級功能-序號」組成），讓使用者已勾選的進度在 localStorage 裡不會全部失效；被刪除的功能對應的驗收項直接拿掉。

### 四、重新匯出截圖

原型或流程圖有改時：

```bash
python3 scripts/pm_sync.py export 需求名
```

匯出服務沒開時它會告訴你，在回覆中提醒使用者按工作台上方的「啟動」再按一次「變更」，或自己在預覽裡點匯出。

### 四之二、程式與測試（已開發時）

文件改完後，受影響的程式依對應的開發工作流修改（`pm-backend.md`、`pm-app.md`、`pm-frontend.md`），測試依 `pm-qa.md` 更新，最後請使用者在右欄「QA」按「全部執行」確認。QA 分頁在規格比上次測試新時會提醒結果可能過時。

### 五、一致性自查

1. PRD 跑 `validate_prd.py`，必須通過（它也會抓殘留的修改標記與刪除線）。
2. 原型照 `pm-prd.md` §3.6 逐頁對照 PRD。
3. 技術規格、驗收清單、上線文件：搜尋變更前的舊值（例如舊的數字、舊的按鈕文字），確認全專案已無殘留：
   ```bash
   grep -rn "舊值" 需求名/
   ```
4. `DESIGN.md` 有改時，跑 `pm-design.md` 流程 C 的 hallmark audit 抽查一個原型。

### 六、記下「現在全部一致」

`pm_sync.py status 需求名` 顯示沒有落後項後：

```bash
python3 scripts/pm_sync.py mark 需求名
```

還有落後項（例如截圖因服務沒開而無法匯出）就**不要** mark，在回覆中說明還差什麼。

接著提交到 git（不論有沒有 mark 都要提交；歷史只存在 git 裡，不存在文件裡）：

```bash
python3 scripts/pm_sync.py commit 需求名 -m "[需求名] 變更：收藏上限從 50 改為不限（客戶要求）"
```

- 訊息格式：`[需求名] 動作：改了什麼（為什麼）`。**「為什麼」寫在這裡**——文件只留結論，理由與來龍去脈進 commit 訊息，日後要查用 `git log`。
- 動作用這幾個詞：`PRD＋原型`、`變更`、`技術規格`、`原型驗證`、`上線包`、`設計方向`、`需求挖掘`、`驗收清單`、`資料分析`。
- 一次變更一個 commit；使用者一次提了好幾件事，訊息裡用分號列出。
- 只提交本需求資料夾與 `PRODUCT.md`／`DESIGN.md`，不碰使用者其他檔案。不 push，推送由使用者決定。
- 專案不是 git 儲存庫或還沒設定作者時，指令會說明原因；照實轉告使用者，不要自己改 git 設定。

### 七、回覆使用者

三到五行：改了什麼、動了哪幾份文件、commit 編號、還有什麼要他處理（例如要重新匯出截圖、要通知工程師 Spec 有變）。**這段說明只出現在對話裡與 commit 訊息，不寫進任何文件。**

使用者問「之前為什麼這樣改」「上次改了什麼」時，用 `git log --oneline -- 需求名/` 與 `git show <編號>` 查，照實回答。

若使用者提出的約束以後也適用（「以後都不要彈窗」），覆寫進 `.pm-workflow/context/[需求名].md` 的約束段。

## 不要做的事

- 不建立變更單、變更紀錄、版本比較文件（歷史在 git）
- 不在文件裡保留舊版內容或修改痕跡
- 不為了「保險」另存副本（匯出服務寫入 HTML 前本來就會自動備份到隱藏的 `.handoff/html-backups/`）
- 不只改使用者點名的那一處就結束
