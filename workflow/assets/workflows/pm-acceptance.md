# PM功能驗收清單工作流

本工作流旨在幫助產品經理在研發提測後或上線前，快速生成結構化的自測清單，確保核心業務流程走通、異常分支被處理、UI高保真還原。

## 適用場景
- 研發提測後的 PM 走查（Sanity Check）
- 上線前的產品功能驗收
- 視覺/互動還原度核對

## 需求目錄歸屬規則（落盤前必讀）
> 產物按「需求名」收納，誰先開工誰建家。本工作流通常**基於已有 PRD**，故該需求的 `[需求名]/` 多半已存在。
1. 清單落盤前，先查專案根目錄是否已存在該需求同名資料夾 `[需求名]/`：**已存在則沿用**，把清單放進它的 `驗收清單/` 子目錄；**不存在則以需求名新建** `[需求名]/`，再建 `驗收清單/`。
2. 驗收的 PRD 來源應取自同一需求目錄 `[需求名]/需求文件/`，保持需求名完全一致。
3. 只建當前用到的子目錄（這裡是 `驗收清單/`），不預建空資料夾。`scripts/`、`.handoff/` 等共享資源仍在專案根目錄。

## 執行步驟

### Step 1: 讀取 PRD 原始檔
1. 詢問使用者需要驗收的 PRD 檔案路徑（通常位於 `[需求名]/需求文件/` 目錄下）。
2. 完整讀取該 HTML 檔案。
3. 提取 PRD 中的：功能模組拆解（詳細方案每一行）、跨頁共享規則、每一行的【邊界說明】、資料埋點表。有技術規格時也讀 `[需求名]/技術規格/` 的測試重點。

### Step 2: 拆解驗收維度
將提取的內容轉化為可執行的 Check-list，分類如下：
1. **核心流程**：主線路徑是否暢通（如：進入入口 -> 填寫內容 -> 提交成功 -> 狀態更新 -> 檢視結果）。優先順序 P0。
2. **邊界與異常**：網路斷開、超時、無權限、次數用盡、不合規輸入等邊緣場景的處理。優先順序 P0/P1。
3. **UI 還原度**：關鍵頁面的佈局、顏色、互動動效、載入狀態是否與需求/原型一致。優先順序 P1/P2。
4. **資料埋點**：核心轉化漏斗的埋點是否觸發（如果有條件驗收）。

### Step 3: 生成《功能驗收清單》HTML
1. 產物按需求名分資料夾：在 `{需求名稱}/驗收清單/` 子目錄中建立 HTML（該需求頂層目錄不存在則先建立）。
2. 檔案命名規範：`{需求名稱}/驗收清單/{需求名稱}-驗收清單.html`。
3. **UI 與互動規範**：
   - 使用現代化、清爽的介面風格（淺色為主，類似 Notion/Linear）。
   - **三態選擇器**：每個驗收項透過點選在“✅ 通過”、“❌ 未通過”、“⏭️ 跳過”之間切換。
   - **進度統計**：頂部懸浮展示通過率進度條，以及各狀態的數量統計。
   - **過濾功能**：支援按狀態篩選列表（全部、待驗收、通過、未通過）。
   - **模組摺疊**：支援按一級模組摺疊/展開驗收項。
   - **本地儲存**：使用 `localStorage` 自動儲存驗收進度。每個驗收項帶穩定的 `data-id`（「一級模組-二級功能-序號」，只用中英文、數字與連字號，例如 `提醒-新增-1`），放在該驗收項的元素上。PRD 變更後重新產生清單時，已勾選的進度不會全部失效；自動測試也用這個編號對應（`[驗收 需求名:提醒-新增-1]`），工作台 QA 分頁會顯示每一項有沒有自動測試、有沒有通過。驗收項用 JavaScript 資料陣列動態產生時，陣列裡每個項目也要有 `id` 與描述欄位（`title` 或 `text`），工作台會直接讀原始碼裡的陣列。
   - **匯出能力**：底部提供“一鍵匯出驗收報告”按鈕，生成 txt 或簡易彙總文字下載。

## 只留最新版

清單只有一份。PRD 改了，走 `pm-change.md` 重新產生並覆寫；被刪除的功能對應的驗收項直接拿掉，不標「已取消」。

## 輸出交付物
- 可互動的功能驗收清單 (`{需求名稱}/驗收清單/{需求名稱}-驗收清單.html`)
