# 除錯工作流

> 使用者回報問題，或 QA 分頁的測試失敗、按下「交給除錯」時使用。
> 順序固定：**重現 → 找原因 → 修正 → 驗證 → 提交**。不跳過重現，不猜。

## 觸發方式

- 使用者說「壞了」「錯誤」「debug」「為什麼不能…」「這個跑不起來」
- 工作台 QA 分頁的「交給除錯」（訊息會帶測試名稱、檔案、錯誤內容）
- 工作台按「QA → 除錯」

## 一、弄清楚現象

整理成三句：**做了什麼 → 預期什麼 → 實際發生什麼**。缺資訊時先看手邊有的：

- QA 帶來的錯誤訊息與堆疊
- 工作台右欄各服務的日誌（使用者可以貼給你；在提示裡也可能已附上）
- 相關的技術規格與 PRD：確認「預期」本身是對的。**如果是規格沒寫清楚或寫錯，這不是 bug**，說明後請使用者走「變更」。

還是不夠就問使用者最少的問題（例如「用哪個測試帳號？在 APP 還是網站？」），以編號清單作為本輪最後的回覆。

## 二、重現

- 有失敗的測試 → 先單獨跑那一個測試，確認能重現。
- 沒有測試 → 寫一個能重現問題的測試（名稱帶 `[驗收 需求名:編號]` 標記，找不到對應驗收項就不帶），先確認它**會失敗**。
- 需要服務在執行才能重現，請使用者在右欄啟動；不要自己啟動開發伺服器。

無法重現時不要改程式。說明你試了什麼、可能的環境差異，請使用者補資訊。

## 三、找根本原因

- 從錯誤點往回追資料流，找到**第一個出錯的地方**，不在症狀處打補丁（例如不要用 try/catch 吞掉錯誤、不要把預期值改成實際值讓測試通過）。
- 常見原因：設定或環境變數（先確認工作台帶入的值）、權限規則、資料格式不一致、非同步時序、前後端對欄位名稱理解不同。
- 設定類問題（連接埠、網址、環境變數）先檢查 `ARCHITECTURE.md` 的 services 設定是否正確；要改那份檔案時請使用者按「系統設計」，不要自己改。

## 四、修正

- **最小修改**，只修這個問題；看到別的問題列在回覆裡，不順手改。
- 資料庫結構要改 → 新增遷移，不改已套用的。
- 修正同時補強：讓當初沒抓到這個 bug 的測試能抓到它。

## 五、驗證

1. 重跑重現用的測試，確認通過。
2. 跑該服務的全部測試，確認沒有把別的弄壞。
3. 涉及畫面的，請使用者在右欄預覽確認。

## 六、提交與回覆

1. `python3 scripts/pm_sync.py commit 需求名 -m "[需求名] 除錯：現象（根本原因）"`，例如 `[疫苗提醒] 除錯：提醒時間錯一天（時區以 UTC 儲存但以本地時間比較）`。
2. 回覆使用者，四行：現象、根本原因、修了什麼、怎麼確認已修好（含要他在右欄按哪裡）。
3. 修正會讓文件與實作不一致時（例如發現規格的邊界寫錯），說明並建議走「變更」。
