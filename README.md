# PM Studio 工作流（繁體中文）

給個人工作室用的產品工作流：一個產品專案裝一套，各自決定風格；所有交付物只留最新版。

| 部分 | 位置 | 內容 |
|---|---|---|
| 工作流 | `workflow/` | 需求挖掘、PRD＋原型、流程圖、設計方向、技術規格、原型驗證、驗收清單、資料分析、上線包、變更管理，含本機截圖匯出服務 |
| 設計層 | `design-layer/` | impeccable、hallmark、pencilplaybook、gsap-skills、ui-ux-pro-max、design-md-chrome（Chrome 擴充） |
| 工作台 | `console/` | 每個專案一個瀏覽器前台：對話下指令、13 顆工作流按鈕、即時預覽、待同步提示 |
| 專案總覽 | `hub/` ＋「開啟專案總覽」 | 所有專案、所有需求的進度軌道與待同步文件，一鍵開啟各專案工作台 |

## 安裝（每個產品專案一次）

```bash
python3 pm-studio/install.py --project /路徑/產品A
```

Windows 用 `py -3`。可重複執行更新；對話紀錄、`PRODUCT.md`、`DESIGN.md`、你改過的工作流檔都保留。安裝時會自動登記到專案總覽。

Chrome 擴充功能要手動載入一次（步驟在安裝後專案裡的 `設計層說明.md`）。

## 日常使用

- **一個專案**：雙擊專案裡的「開啟PM工作台」。
- **所有專案**：雙擊本套件裡的「開啟專案總覽」，從這裡看進度、開任一專案的工作台。

新產品的順序：

1. 「設計方向」→ 建立 `PRODUCT.md` 與 `DESIGN.md`（只問一個問題就能開始）
2. 「需求挖掘」（選用）→ 訪談逐字稿、評論、回饋放進需求的 `素材/`，聚類成痛點與機會；還沒有真實材料時，你可以自己寫 PM 模擬（Claude 給範本、不代寫），報告會把它標成「假設，待驗證」，和真實材料分開算
3. 「PRD＋原型」→ 原型一律依 `DESIGN.md`
4. 「檢查原型」→ hallmark 打分，必修項自動改
5. 「原型驗證」（選用）→ 測試腳本 → 你去測 → 整理結果 → 落回文件
6. 「技術規格」→ 給工程師的 Spec
7. 「驗收清單」→ 開發完成後勾選
8. 「上線包」→ 版本說明、上線檢查清單、落地頁、商店文案、定價

任何時候需求有調整：按「**變更**」，所有受影響的文件一起改到一致。

## 開發：先選技術，工作台跟著變

按鈕分成六組：產品、設計、系統、開發、QA、調整。

**技術選型每個案子都不同，一律先討論。** 選「系統 → 系統設計」，Claude 會依產品需求（平台、原生功能、資料、規模、整合、誰維護、時程預算）替 APP、前端、後端各提 2–3 個選項和取捨，等你決定後才寫 `ARCHITECTURE.md`。選了什麼寫在文件開頭的 `stack` 與 `services`，為什麼選寫在 git 提交訊息。

之後的「開發 → 後端／APP／前端」都照 `ARCHITECTURE.md` 的選型做；「系統 → 技術規格」開頭的 `manifest` 列出這個需求要做的資料表、API、畫面、頁面，右欄用它對照進度。

### 右欄會依選型出現對應分頁

| 支援程度 | 技術 | 右欄能做什麼 |
|---|---|---|
| 專屬面板 | Supabase | 資料庫、帳號與身分切換、測試信箱、檔案、後端函式立即執行、API 測試、建置進度；標題列有啟動燈號 |
| 專屬面板 | Flutter | 手機外框的網頁預覽、模擬器啟動與畫面、熱重載、DevTools、建置進度 |
| 專屬面板 | Next.js | 網站預覽（桌機／平板／手機）、網址列、自動從資料夾判斷頁面進度 |
| 通用支援 | 其他任何能在本機用指令啟動的技術（Vue、Vite、Expo、Django、FastAPI、NestJS、Laravel…） | 啟動與停止、日誌、網頁預覽、自訂後端的 API 測試台（有 OpenAPI 就列出端點）；進度靠程式裡的 `pm-page:`／`pm-screen:`／`pm-endpoint:` 標記 |

還沒做系統設計的專案，右欄會出現「開發」分頁提醒你先選技術；已經有 `supabase/`、`app/`、`web/` 程式但還沒寫 `stack` 的舊專案，工作台會自動偵測。

**點建置進度看規格與實作**：在後端的建置進度點一張資料表、一個資料庫函式或一支 API，會並排顯示「技術規格寫的」和「系統目前實際的」（Supabase 讀資料庫欄位，自建後端讀 OpenAPI），並列出「規格有、實作還沒有」與「實作有、規格沒寫」的欄位；API 另有「在 API 測試台試試」自動帶入方法與路徑。

**連線設定自動處理**：工作台啟動各服務時會帶入本機後端的網址與公開金鑰（網站寫 `.env.local`，Flutter 用 dart-define）；Android 模擬器連不到 `127.0.0.1`，會自動換成 `10.0.2.2`。每個專案、每個服務用不同連接埠，可以同時開。

**權限自動跟著選型**：`ARCHITECTURE.md` 的 `tools` 列的開發指令會允許 Claude 執行；各服務的啟動指令由工作台負責，會自動禁止 Claude 執行。連到遠端資料庫或部署的指令一律封鎖。

**設計 token**：`scripts/pm_tokens.py` 把 `DESIGN.md` 轉成 Flutter（dart）、網站（css）、React Native（ts）用的檔案，程式裡不手寫色碼。

**安全網**：「系統」和「開發」兩組的每一輪，執行前工作台會先做 git 快照；回覆下方有「退回這一輪」。改過資料庫的話，退回後到後端按「重置測試資料」。

**本機需要的工具依選型而定**：Supabase 要 Docker Desktop 與 `supabase` 指令；Flutter 要 Flutter SDK（iOS 另需 Xcode）；Node 類框架要 Node.js（建議再裝 pnpm）；其他技術依它自己的需求。

## QA 與除錯

- **QA → 自動測試**：Claude 依驗收清單與技術規格，用選定技術的主流測試工具寫測試。測試名稱帶 `[驗收 需求名:驗收項編號]`，就會對應到驗收清單的項目。
- **QA → 除錯**：重現 → 找根本原因 → 最小修正 → 重跑測試 → 提交，理由寫在提交訊息。
- **QA → 驗收清單**：人工驗收用的互動清單，每一項的編號也是自動測試的對應依據。

右欄的「**QA**」分頁：

| 功能 | 做什麼 |
|---|---|
| 全部執行／各服務執行 | 跑測試，標題列顯示每個服務的通過、失敗、略過數 |
| 驗收對照 | 每個驗收項有沒有自動測試、有沒有通過；標錯的編號會列出來 |
| 測試結果 | 失敗的排前面，附錯誤訊息、詳細內容、失敗時的截圖；「交給除錯」一鍵帶入 |
| 日誌 | 測試執行的輸出 |

**任何技術都能接**：測試結果用 JUnit XML 這種共通格式（pytest、Vitest、Jest、Playwright、Go 等都支援）。Flutter 與 Supabase 已內建；其他服務在 `ARCHITECTURE.md` 的 services 寫 `test`（測試指令）與 `test_report`（報告位置）。

**服務依賴**：services 寫 `depends_on: [db]`，啟動 API 時會自動先把資料庫開好。

技術規格或 PRD 比上次測試新時，QA 分頁會提醒結果可能過時。

## 更新所有專案

更新這個套件後，打開專案總覽按「**更新所有專案**」，或在終端機執行：

```bash
python3 install.py --all
```

對話紀錄、`PRODUCT.md`、`DESIGN.md`、`ARCHITECTURE.md`、需求文件與程式都不會被動到。開著的工作台要關掉重開。更新後，工具檔（`scripts/`、`.agents/`、`.claude/`、啟動檔）會自動提交一次，不會一直掛在「未提交」。

## 只留最新版

- PRD 沒有版本記錄章節，不留刪除線與「已修改」標記；最後更新日期寫在專案資訊。`validate_prd.py` 會擋下殘留的修改痕跡。
- 不另存舊檔、不建變更單。歷史在 git（見下一節）。
- Claude 續接工作所需的現況（進度、你的偏好與約束、未決問題）存在隱藏檔 `.pm-workflow/context/需求名.md`，每次覆寫。

## 歷史存在 git

文件只留結論，**為什麼改、改了什麼**寫在 git 的提交訊息裡。

- 安裝器會把專案初始化成 git 儲存庫並做第一次提交（專案本來就在 git 裡則不動）。
- Claude 每完成一件工作就提交一次，訊息格式是 `[需求名] 動作：改了什麼（為什麼）`，例如 `[課程收藏] 變更：收藏上限從 50 改為不限（客戶要求）`。
- 想查以前的決定，直接在工作台問 Claude「上次為什麼改收藏上限」，它會查 git 紀錄回答；或自己用 `git log -- 需求名/`。
- Claude 不會 push、不會改你的 git 設定。要推到 GitHub 自己執行 `git push`，建議用**私人儲存庫**。
- 專案總覽會顯示每個專案有幾個檔案還沒提交。
- `素材/` 裡的訪談逐字稿也會被提交。若含個資又要推到雲端，在專案的 `.gitignore` 加一行 `*/素材/`。

第一次使用 git 要先設定作者（只要一次）：

```bash
git config --global user.name "你的名字"
git config --global user.email "你的信箱"
```

## 怎麼知道文件有沒有同步

`scripts/pm_sync.py` 比對上下游：PRD 改了而原型、Spec、驗收清單沒跟上，就標成落後；`DESIGN.md` 改了，所有原型與落地頁都會被檢查。

- 工作台：需求清單顯示「N 份待同步」，預覽上方出現橘色提示和「同步到最新」按鈕
- 專案總覽：進度軌道上落後的節點變成橘色
- 變更完成後，Claude 會自動重新匯出原型與流程圖截圖（需要匯出服務開著）

你直接在瀏覽器裡改 PRD 也偵測得到。

## 專案結構（安裝後）

```
產品A/
├─ PRODUCT.md  DESIGN.md  ARCHITECTURE.md   產品事實 · 設計系統 · 系統設計
├─ [需求名]/
│  ├─ 需求挖掘/  需求文件/  原型/  流程圖/  原型截圖/  流程圖截圖/
│  ├─ 原型驗證/  技術規格/  驗收清單/  資料分析/  上線/
│  └─ 素材/                             你提供的原始材料（不是交付物）
├─ （程式資料夾）                        位置由 ARCHITECTURE.md 的 services 決定，例如 app/、web/admin/、supabase/
├─ .agents/workflows/                   15 份工作流說明書
├─ .claude/skills/  .claude/agents/     設計層
├─ scripts/                             匯出服務、工作台、pm_sync、validate_prd
├─ .pm-workflow/  .pm-console/  .handoff/   隱藏：設定、續接脈絡、同步紀錄、自動備份
├─ 啟動原型匯出服務.command / .bat
├─ 開啟PM工作台.command / .bat
└─ 設計層說明.md
```

## 語言

工作流、工作台、總覽、安裝器、接線說明全部繁體中文（台灣用語）。六組上游設計 skill 保持英文原文以便追更新；Claude 讀英文規則、用繁體回覆。


## 已知限制

- 以模擬的 Claude Code 輸出實測完整流程（安裝兩個專案、PRD → Spec → 手動改 PRD → 偵測落後 → 同步 → 自動重新截圖 → 從總覽開啟另一專案工作台）；真實 Claude Code 與 Windows 實機未測。
- 同步判斷以檔案修改時間為準：只改了檔案裡無關緊要的地方也會被標成落後，這時按「同步到最新」，Claude 確認沒有要改的就會直接標記一致。
- 從舊版升級的專案，舊的 `.agents/workflows/edu-pm-*.md` 與 `關鍵點.md` 不會自動刪除，可手動刪掉。
- impeccable 的 `context` / `detect` / `live` 第一次執行要上網下載引擎；Pencil 高保真只在 macOS 可用。
